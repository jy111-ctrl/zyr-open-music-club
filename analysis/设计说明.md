**交互流程**
1. 选示例 → OfflineAudioContext 现场合成 → 得到 AudioBuffer

## 3. 内置 4 段程序化音频

全部用 `OfflineAudioContext` 现场合成，**不存任何音频文件**。

| # | 名称 | 编曲 | 参数 | 时长 | 主要考察 |
| --- | --- | --- | --- | --- | --- |
| 1 | 鼓点 120 | 4/4 底鼓 + 军鼓 + 闭合踩镲 | 120 BPM，C 小调无调性 | 8s | BPM 估计 |
| 2 | 和弦 C | C–Am–F–G 四和弦循环 | 三角波 + 正弦，ADSR 包络 | 8s | 调性 / chroma |
| 3 | 混合 100 | 鼓组 + Am–F–C–G + 贝斯 | 100 BPM | 12s | 综合 |
| 4 | 切分 90 | swing 踩镲 + 切分底鼓 + 七和弦 | 90 BPM | 12s | 区分度（防四段雷同） |

**合成要点**
- 底鼓：正弦扫频 120→45 Hz，指数衰减 0.35s
- 军鼓：白噪声 + 带通 1.8 kHz + 短包络
- 踩镲：白噪声 + 高通 6 kHz，衰减 0.06s
- 和弦：每个音 2～4 个正弦叠加，包络 attack 10ms / decay 250ms / sustain 0.6 / release 400ms
- 贝斯：正弦 + 轻微饱和，跟随根音

**播放**：直接用 `AudioBufferSourceNode` 播放（不进全站播放器，避免污染现有队列模型），进度条由 `requestAnimationFrame` 驱动。

## 4. 分析算法（Web Worker 内执行）

```
AudioBuffer (mono)
   │
   ├─ ① FFT：窗长 2048 / hop 512 / Hann 窗 → 每帧幅度谱
   │      └→ 波形峰值（每像素 min/max）
   │      └→ 频谱图（log 幅度 → 色阶 → ImageData）
   │
   ├─ ② 频谱通量（spectral flux）→ 起音包络
   │      └→ 自相关 → BPM（限制 60–180，取首个强峰）
   │      └→ 节拍数 = 峰值个数
   │
   ├─ ③ Chroma：把 FFT bin 折叠到 12 个音级
   │      └→ 24 个调性模板（Krumhansl major/minor）→ 相关 → 最佳调性
   │
   └─ ④ 响度：RMS → dBFS；频谱质心 → 音色亮度
```

**识别（与 4 段比对）**

特征向量：
```
v = [ chroma(12, 归一化), BPM/180, onsetDensity, centroid/8000 ]
score = cosine(v, v_lib) × tempoPenalty
tempoPenalty = 1 − min(1, |log2(bpm/bpm_lib)| × 0.8)
```
输出按 score 降序，第一名即识别结果，score ≥ 0.75 判为「高置信」。

> 为什么不用指纹（chromaprint）：课程场景下 4 段库太小，指纹的优势发挥不出来，而 chroma + BPM 对合成音频的区分度已经足够，且算法可解释、答辩讲得清。

## 8. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| `OfflineAudioContext` 需要用户手势才能播放 | 打开页面自动合成会静默失败 | 合成不需要手势，**播放**才需要；首次播放由点击触发 |
| 分析阻塞主线程 | 页面卡顿 | 全部放 Worker，主线程只画 canvas |
| 频谱图 canvas 像素量大 | 高 DPI 屏发虚 | 按 `devicePixelRatio` 缩放画布 |
| 4 段音频区分度不够 | 识别率虚高、答辩被质疑 | 刻意设计 4 种不同 BPM（120/自由/100/90）与不同调性 |
| Worker 中无法用 DOM | 不能直接画图 | Worker 只回传数值数组，绘制在主线程 |

---

## 9. 答辩可以讲的三个点

1. **零素材依赖**：示例音频由代码合成，不存在版权与资源缺失问题，任何环境都能复现
2. **算法可解释**：FFT → 频谱通量 → 自相关 → BPM；chroma → 调性模板相关；特征余弦相似度
3. **有量化证据**：12 个变体用例的识别率表格，而不是“看起来能用”
