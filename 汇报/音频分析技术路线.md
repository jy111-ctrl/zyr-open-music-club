# 音频分析模块 · 技术路线与产出溯源

> 模块位置：`frontend/src/features/analysis/`
> 日期：2026-11-03
> 目标：说明"屏幕上每一个数字/图形，是从哪一步算出来的"

---

## 一、两条独立的数据链路

整个模块不是一条管线，而是**两条并行链路**，各有用途：

```
链路 A（实时）  播放中的 <audio> ──AnalyserNode──► 每帧采样 ──► 播放器条 / 声纹弹窗
链路 B（离线）  当前音轨 URL ──fetch──► decodeAudioData ──► 整曲统计 ──► 声纹档案
```

| | 链路 A 实时 | 链路 B 离线 |
| --- | --- | --- |
| 数据来源 | 正在播放的音频流 | 完整音频文件 |
| 时间范围 | 当前时刻（滚动窗口 6s/30s） | 整首歌（默认前 120s） |
| 输出 | 频谱柱、瀑布图、BPM、dBFS、DR | 波形、整曲频谱、Mel、MFCC、分段 BPM |
| 触发 | 播放即开始 | 点「生成整曲档案」 |
| 代价 | 极低（每帧一次 FFT） | 较高（解码 + 240 次 FFT） |

## 二、链路 A：实时声纹

### 2.1 音频从哪里来

```
<audio crossOrigin="anonymous">          ← 上游 player-core 创建
   ├─ 上游 createAudioAnalysis(audio)    ← 已有：自建 AudioContext + AnalyserNode
   │     └─ read(now) → {low, mid, high, activity, spectrum}
   └─ 我们 captureStream()                ← 新增：抓一条 MediaStream
         └─ createMediaStreamSource → 我们的 AnalyserNode
```

**为什么不用 createMediaElementSource**：浏览器规定同一个 `<audio>` 只能创建**一个** MediaElementSource。上游已经占用了，我们再建会抛 `InvalidStateError`。

**captureStream 的关键细节**：

- 抓到的流必须接到 `destination` 才会被持续驱动，否则数据恒为 0
- 但不能出声（会与播放器叠加、产生回声），所以中间加一个 **0 增益的 GainNode** 当"静音汇点"

```ts
source.connect(analyser)
analyser.connect(silentGain)   // gain = 0
silentGain.connect(destination)
```

### 2.2 采样与整形

```
每 32ms（约 30fps）采样一次
   ├─ getFloatTimeDomainData → 2048 点时域
   │     ├─ RMS → 20log10 → dBFS
   │     └─ max|x| → 峰值（0..1）
   ├─ getByteFrequencyData → 1024 个频点（0..255）
   │     ├─ 40–200Hz 平均 → 低频能量（节拍包络用）
   │     └─ 40Hz–10kHz 对数分带 → 128 行绝对 dB 频谱
   └─ 短时 RMS 历史（每 100ms 一条，保留 30s）→ 动态范围
```

### 2.3 各产出的算法

| 产出 | 数据来源 | 算法 | 参数 |
| --- | --- | --- | --- |
| **频谱柱（32 根）** | 128 行频谱 | 每 4 行取最大值 | 32 段 |
| **瀑布图** | 绝对 dB 频谱 | 逐帧画 1px 竖列，整体左移 | 128 行，gamma 1.5 |
| **响度 dBFS** | 时域 RMS | `20·log10(rms)`，再做 EMA 平滑 | 平滑系数 0.25 |
| **峰值** | 时域 max | `max|x|` | 0..1 |
| **动态范围 DR** | 100ms 短时 RMS | P95 − P10，过滤 −60dB 以下，上限 30dB | 30s 窗口 |
| **BPM** | 低频能量包络 | 峰值检测 → 间隔中位数 → 折算到 60–180 | 6s 窗口，最近 7 次取中位数 |

### 2.4 BPM 的具体步骤

```
① 每 40ms 记录一次低频能量 → 得到包络序列（最多 6 秒 ≈ 150 点）
② 去均值 → 找局部极大值（centered[i] > 0 且大于左右邻居）
③ 相邻峰值时间差 dt，只保留 200ms < dt < 2000ms（对应 30–300 BPM）
④ 取 dt 的中位数 → bpm = 60000 / median
⑤ 折叠到 60–180：小于 60 乘 2，大于 180 除 2
⑥ 最近 7 次结果取中位数（抑制跳变）
```

**为什么用中位数而不是均值**：节拍漏检会产生"双倍间隔"的离群值，均值会被带偏，中位数更稳。

### 2.5 颜色映射（决定"看得出层次"）

```
dB = -100 + (byte / 255) × 70      // Chromium: byte 0 ↔ -100dB, 255 ↔ -30dB
normalized = (dB - (-85)) / ((-5) - (-85))
alpha = normalized ^ 1.5
```

**这是模块里最关键的一次修正**：早期版本用的是上游 `bands.spectrum`，它按"每帧最大值"归一化，唱得再轻也满格 → 画面全亮、没有层次。改成**绝对 dB 刻度**后，低频（约 −20dB）亮、高频（约 −60dB）暗，层次才出来。

### 2.6 绘制要点

- **瀑布图不能用带 DPR 的变换做自拷贝**，否则每帧按 devicePixelRatio 放大 → 逐帧模糊成色块
- 正确做法：`setTransform(1,0,0,1,0,0)` 下 `drawImage(canvas, -ratio, 0)`，即按**设备像素**左移
- 刻度是独立 DOM 层，**不画进 canvas**（否则会被每帧左移拖成残影）

## 三、链路 B：声纹档案（离线）

### 3.1 取数与解码

```
audio.currentSrc → fetch() → ArrayBuffer
   → new AudioContext().decodeAudioData(buffer.slice(0))
   → AudioBuffer（PCM 浮点，双声道）
```

- 传 `slice(0)` 是因为 `decodeAudioData` 会**分离（detach）**传入的 ArrayBuffer
- 只分析前 **120 秒**：4 分钟立体声解码约占 80MB 内存，课程环境需要设上限

### 3.2 单声道化与波形

```
mono[i] = (left[i] + right[i]) / 2
波形：900 个桶，每桶记录 min / max
```

用 min/max 而不是采样点，是因为抽稀后**峰值包络**才保留音量的真实起伏（直接取每 N 个点会丢峰值）。

### 3.3 STFT 与对数频谱

```
窗长 1024（Hann 窗），hop = (总采样数 - 1024) / 240 → 240 列
每列：加窗 → radix-2 FFT → 幅度谱（512 个频点）
分带：40Hz–10kHz 对数划分 64 行，每行取该带内最大幅度
归一化：除以全局最大 → ^0.45 → ×255
```

| 参数 | 取值 | 为什么 |
| --- | --- | --- |
| 窗长 1024 | 44.1kHz 下 23ms | 时间分辨率够（鼓点）、频率分辨率 43Hz（够分谐波） |
| Hann 窗 | 0.5−0.5cos | 旁瓣衰减好，减少频谱泄漏 |
| gamma 0.45 | 提亮弱能量 | 线性映射会让 90% 的区域全黑 |

### 3.4 Mel 频谱

```
mel(f) = 2595 × log10(1 + f/700)
64 个三角滤波器，覆盖 20Hz–8kHz，相邻 50% 重叠，按面积归一化
能量 → 10log10 → 以全局最大为参考，向下 80dB 映射到 0..255
```

- **面积归一化**必不可少：高频滤波器更宽，不归一化会天然占优
- **80dB 动态范围**：再大就全灰，再小只剩峰值

### 3.5 MFCC

```
Mel 能量（64 维）→ 取自然对数 → DCT-II → 前 13 个系数
逐系数做 min/max 归一化 → 13 × 240 的热力图
```

- `c0` ≈ 整体能量，`c1–c12` ≈ 音色形状
- **逐系数归一化**是关键：c0 的量级远大于其他系数，统一归一化会把 c1–c12 压成一条线

### 3.6 分段 BPM

```
每 15 秒一个窗口，窗口内用 20ms RMS 包络，
套用与实时 BPM 相同的「峰值检测 + 间隔中位数」算法
```

于是得到"前奏 78 → 副歌 132 → 尾奏 96"这样的走向。

### 3.7 导出 PNG

新建 960×700 画布 → 依次 `drawImage` 已渲染的波形/频谱 canvas → 叠加标题、指标、分段柱 → `toBlob` → 触发下载。

## 四、模块结构与调用关系

```
features/analysis/
├─ bands.ts          上游频段注册表（register / read）
├─ capture.ts        captureStream 采集：dBFS / 峰值 / DR / 低频 / 绝对 dB 频谱
├─ audio-analysis.ts 实时整形：32 柱 / 128 行 / BPM / 平滑 → 对外 subscribe
├─ overlay.ts        播放器条 + 声纹弹窗（瀑布图、刻度、指标）
├─ profile.ts        离线分析：波形 / 对数谱 / Mel / MFCC / 分段 BPM
└─ profile-view.ts   档案页：三视图切换、导出 PNG
```

```
player-core.ts（上游，改动 2 行）
   ├─ registerAudioBands(analysis)   → bands.ts
   └─ registerAudioElement(audio)    → capture.ts

main.ts（上游，改动 2 行）
   └─ mountAnalysisOverlay()         → overlay.ts
```

## 六、踩过的坑（可作为"工程经验"写进报告）

| 现象 | 根因 | 解决 |
| --- | --- | --- |
| 频谱全亮、无层次 | 上游 spectrum 按每帧峰值归一化 | 改用 capture 的绝对 dB 频谱 |
| 数据恒为 0 | MediaStream 源没有接到 destination | 加 0 增益静音汇点 |
| 界面读到 0，日志有数据 | 两个 import 路径被 Vite 当成两个模块 | 统一带 `.ts` 的说明符 |
| 瀑布图逐帧变模糊 | 自拷贝时带了 DPR 变换 | 单位变换下按设备像素位移 |
| 调性永远是 F# major | dB 字节当线性幅度 + 无形状检验 | 改为线性幅度 + 噪声底 + 形状阈值（最终决定移除该指标） |
| 整曲频谱几乎全白 | 先乘 40 再除回去，数值被压扁 | 两遍扫描 + 全局归一化 + gamma |

## 七、已知限制

| 限制 | 影响 | 可改进方向 |
| --- | --- | --- |
| 离线只分析前 120 秒 | 长曲后段无档案 | 分段流式处理 |
| 主线程分片计算 | 分析耗时 2–4 秒 | 移入 Web Worker |
| Firefox 无 captureStream | 实时 dBFS 降级、DR 不可用 | 已在 UI 标注 |
| 分辨率 64 行 / 240 列 | 做和弦识别不够 | 提高行数与 hop 密度 |
| BPM 依赖低频包络 | 无鼓点的歌不准 | 加谱通量 + 动态规划节拍跟踪 |
