# Open Music Club · 网络层次与技术栈说明

> 用途：课程汇报 / 报告章节
> 范围：以当前实现为准（React 前端 + Node 后端 + SQLite + Nginx + Cloudflare/Let's Encrypt）
> 日期：2026-11-03

---

## 一、总览：一条请求要经过哪些层

```
浏览器
  │  ① 应用层    HTTP 请求（GET /api/netease/search?keywords=…，带 Cookie）
  │  ② 表示层    JSON / UTF-8 编码；TLS 加密后的字节流
  │  ③ 会话层    express-session + Redis，Session Cookie，CSRF Token
  │  ④ 传输层    TCP 443（三次握手 / 四次挥手 / 拥塞控制）
  │  ⑤ 网络层    IP 寻址、路由、NAT、安全组
  │  ⑥ 链路层    以太网 / Wi-Fi，MAC 地址，ARP
  │  ⑦ 物理层    光纤 / 双绞线 / 无线电波
  ▼
Cloudflare DNS → 你的服务器（Nginx → Node → SQLite）
  ▲
  └── 反向路径：JSON 响应 → React 渲染 → WebGL 场景 / Canvas 频谱
```

**一句话**：我们写的所有代码都在**应用层及其以上**；下面五层由操作系统、网卡、云厂商和浏览器负责，但它们决定了"能不能连上、快不快、安不安全"。

## 二、OSI 七层对照表（本项目实例）

| 层 | 名称 | 本项目具体内容 | 关键证据 / 配置 |
| --- | --- | --- | --- |
| 7 | **应用层** | HTTP/1.1 REST 接口：`/api/auth/*`、`/api/netease/*`、`/api/local/*`、`/api/footprint/*`、`/api/me/*`；DNS 域名解析；SMTP 邮件通知；健康检查 `/health` | Express 5 路由；`GET` 返回 200/401/404/429；错误统一 JSON |
| 6 | **表示层** | JSON 序列化 + UTF-8；WebP 图片转码（sharp，头像统一 512×512）；SVG 封面；MP3/WAV 音频解码；TLS 加密（现代实现把加密放在表示层职责） | `sharp().webp({quality:80})`；`Content-Type: application/json; charset=utf-8` |
| 5 | **会话层** | `express-session` + Redis 会话存储；Cookie `open_music_club.sid`（`httpOnly` / `SameSite=Lax` / 生产 `Secure`）；空闲 480 分钟超时；TOTP 双因素；CSRF Token | `connect-redis`；`RedisStore`；`X-CSRF-Token` 头校验 |
| 4 | **传输层** | TCP 承载 HTTP/HTTPS；端口 443 / 80 / 3000 / 6379 / 8123；Keep-Alive 复用；UDP 用于 DNS 查询与 Cloudflare 隧道 | Nginx `proxy_http_version 1.1`；`server.keepAliveTimeout=5000` |
| 3 | **网络层** | IPv4 公网 IP、子网与路由、NAT（家庭宽带需端口转发）、云安全组、CDN 调度 | 域名 A 记录 → 服务器 IP；网易云音频走 `m70x.music.126.net` CDN |
| 2 | **数据链路层** | 以太网（服务器网卡）/ Wi-Fi 802.11（用户设备）；MAC 地址；ARP 解析网关 | 云厂商虚拟交换机；同一网段内 ARP |
| 1 | **物理层** | 光纤（云机房上联）、Cat5e/6 双绞线（局域网）、2.4G/5G 无线电（手机/笔记本） | 实测香港节点访问延迟 30–50 ms；家宽上行带宽限制上传速度 |

## 四、一次「点播放」的完整握手时间线

### 阶段 0：DNS 解析（应用层 → 传输层）
```
浏览器 → 本地 DNS 缓存 → 递归解析器 → Cloudflare NS
查询 webkk.xyz 的 A 记录（UDP 53，响应过大时自动切 TCP 53）
返回：服务器公网 IPv4
```

### 阶段 1：TCP 三次握手（传输层）
```
客户端 ──SYN(seq=x)──────────► 服务器 :443
客户端 ◄─SYN+ACK(seq=y,ack=x+1)─ 服务器
客户端 ──ACK(ack=y+1)────────► 服务器
连接建立（三次握手解决：双方收发能力确认 + 序列号同步）
```
- 使用 **443 端口**（HTTPS），Nginx 监听
- 支持 Keep-Alive：同一条连接可复用多次请求，减少重复握手

### 阶段 2：TLS 握手（表示层 / 安全）
```
ClientHello  → SNI=webkk.xyz, ALPN=h2/http1.1, 支持的套件, 密钥共享
ServerHello  ← 选定套件, 证书链（Let's Encrypt）, 密钥共享
双方计算会话密钥 → Finished
```
- 版本：TLS 1.2 / 1.3（1.3 通常 **1-RTT**，会话复用可 0-RTT）
- 证书：`certbot` 自动签发与续期，Nginx 加载 `fullchain.pem` / `privkey.pem`
- 之后所有 HTTP 明文都在加密信道内传输

### 阶段 3：HTTP 请求（应用层）
```http
GET /api/netease/search?keywords=周杰伦 HTTP/1.1
Host: webkk.xyz
Cookie: open_music_club.sid=…
X-CSRF-Token: …            ← 写操作才需要
Accept: application/json
```

### 阶段 4：服务端处理链
```
Nginx（终结 TLS）
  ├─ /            → 直接返回 frontend/dist 静态文件（HTML/JS/CSS）
  └─ /api/*       → 反向代理到 127.0.0.1:3000（同机回环，不再经过网卡）

Node + Express 中间件链：
  requestId → HTTPS 强制 → helmet(CSP/HSTS) → 同源 CORS
  → JSON 解析(1MB 限制) → Session(Redis) → 全局限流
  → CSRF 校验 → 登录态校验 → 路由 → Service → SQLite(WAL)
```

### 阶段 5：响应与渲染
```
JSON 响应（gzip 压缩）→ 浏览器
  ├─ React 19 挂载视图
  ├─ Three.js 初始化 WebGL 上下文 → GPU 渲染 3D 档案墙
  └─ Canvas 2D 绘制波形 / 频谱瀑布（每帧 requestAnimationFrame）
```

### 阶段 6：音频流（独立连接）
```
<audio crossOrigin="anonymous"> → GET 音频 CDN（Range: bytes=0-）
  ← 206 Partial Content + Access-Control-Allow-Origin: *
  → 浏览器解码 MP3 → AudioContext
  → MediaElementSource → AnalyserNode(FFT 2048) → 32 根频谱柱 / 128 行瀑布图
```
> 关键点：音频是**独立的一条 TCP 连接**，与页面 API 请求互不影响；
> CDN 返回 206 说明支持**分片下载**，可边下边播、可拖动进度条。

## 五、协议与端口清单（汇报可直接用）

| 协议 | 用途 | 端口 | 层次 | 是否公网暴露 |
| --- | --- | --- | --- | --- |
| HTTPS (TLS 1.2/1.3) | 浏览器 ↔ Nginx | 443 | 应用/表示 | ✅ 唯一入口 |
| HTTP | ACME 校验 + 跳转 HTTPS | 80 | 应用 | ✅ 仅跳转 |
| HTTP/1.1 | Nginx ↔ Node | 3000（127.0.0.1） | 应用 | ❌ 仅回环 |
| Redis 协议 (RESP) | Node ↔ Redis（会话/限流） | 6379（127.0.0.1） | 应用 | ❌ 仅回环 |
| HTTP | Avatar 子站 | 8123（127.0.0.1） | 应用 | ❌ 经反向代理 |
| DNS | 域名解析 | 53（UDP/TCP） | 应用/传输 | — |
| SMTP | 邮件通知（可选） | 465 / 587 | 应用 | 出站 |
| TCP | 上述所有连接的承载 | — | 传输 | — |
| UDP | DNS 查询、QUIC（隧道） | 53 / 443 | 传输 | — |

**没有使用的协议**（答辩可能被问）：
- **WebSocket**：本项目所有交互都是请求-响应式，无服务器主动推送需求
- **MQTT / CoAP**：无物联网设备接入
- **gRPC**：单体前后端，REST 足够
- **FTP**：文件上传走 HTTP multipart

| 位置 | 语言 / 运行时 | 框架 / 关键库 |

| 浏览器 | TypeScript + JSX → 编译为 JS | React 19、Vite 7、Three.js（WebGL）、Canvas 2D、Web Audio API |

## 七、安全措施在各层的分布（汇报加分点）

| 层 | 措施 |
| --- | --- |
| 应用层 | 输入校验、参数长度限制、统一错误脱敏（不暴露堆栈）、CSRF Token、限流（登录 10 次/15 分钟） |
| 表示层 | 图片重编码剥离元数据（防隐藏信息）、响应头 CSP/HSTS/X-Content-Type-Options |
| 会话层 | Session 存 Redis（不在 JWT 里塞权限）、Cookie httpOnly + SameSite + Secure、TOTP 二次验证 |
| 传输层 | 仅开放 443（80 只做跳转）、内部服务只监听 127.0.0.1 |
| 网络层 | 云安全组白名单、管理端口限来源 IP |
| 物理层 | 云机房物理隔离（由服务商保障） |

## 八、汇报时可能被追问的三个问题

**Q1：为什么不用 WebSocket 做实时？**
本项目没有"服务器主动推送"的场景：播放状态、频谱分析都在浏览器本地完成，数据变更由用户操作触发。引入 WebSocket 会增加连接管理与鉴权复杂度，收益为零。

**Q2：TLS 在哪一层终结？**
在 Nginx（反向代理）处终结。Node 只监听 `127.0.0.1:3000`，收到的是明文 HTTP。这样 Node 不承担证书管理，性能更好；代价是**内网到 Node 这一段是明文**，所以强制只绑定回环地址。

**Q3：为什么用 SQLite 而不是 MySQL？**
单机、单实例、成员规模小（<100 人），SQLite（WAL 模式）足够，且零运维成本。它的限制是**只支持单写者**，所以部署上只能跑单实例；若将来需要多实例，必须迁移到 PostgreSQL。

## 九、一句话总结（可做结尾页）

> 我们的代码集中在**应用层**（HTTP/JSON/REST），通过**会话层**的 Cookie+Redis 保持登录态，
> 依赖**传输层**的 TCP 保证可靠传输、**表示层**的 TLS 保证机密性；
> 而**网络层及以下**（IP、路由、以太网、光纤）由云厂商与运营商保障——
> 这也解释了为什么部署时最常遇到的问题不是代码，而是 DNS 记录、安全组端口和 NAT 转发。
