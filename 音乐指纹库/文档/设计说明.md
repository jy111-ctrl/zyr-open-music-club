# 音乐指纹库 · 设计说明

## 1. 目标

在音频分析板块内加入「听歌识曲」：库里只有 1 首歌，用它的不同版本（原曲、加噪、切断、清唱）测试能否认出。

## 2. 原理（迷你 Shazam）

```
建库                                        识别
─────────────────────────────────────────────────────────
解码 → 重采样 11.025kHz                    解码片段
  → STFT（窗 1024 / hop 256）                 → 同样的 STFT
  → 二维局部峰值（常数图）                     → 提取峰值
  → 峰值配对 (f1, f2, Δt) → 哈希              → 生成查询哈希
  → 存入 IndexedDB                          → 查表命中
                                            → 按 (歌曲, 时间偏移) 投票
                                            → 票数最高者胜
```

**为什么用时间偏移投票**：查询片段可以从歌曲任意位置开始，只有真正的匹配会让大量哈希落在同一个偏移上。

## 3. 关键参数

| 参数 | 取值 | 原因 |
| --- | --- | --- |
| 采样率 | 11025 Hz | 够覆盖 4kHz 以内的音乐结构，计算量小 |
| FFT 窗 | 1024 | 频率分辨率约 10.8Hz |
| hop | 256（约 23ms） | 时间分辨率足以捕捉节拍 |
| 频率范围 | 100–4000 Hz | 避开低频轰鸣与高频噪声 |
| 峰值上限 | 30 个/秒 | 防止密集段把哈希表撑爆 |
| 邻域抑制 | ±4 帧 / ±8 bin | 保证峰值稀疏且稳定 |
| 配对 | 每个峰向后配 5 个，Δt 4–43 帧 | 短 Δt 对帧抖动太敏感 |
| Δt 量化 | 2 帧 | 吸收 ±1 帧的抖动 |
| 频率量化 | 2 bin | 吸收细微频移 |
| 判定阈值 | 票数 ≥ 20 | 反例只有 8 票，真匹配 116+ |

## 4. 调试记录（重要）

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 20 秒片段产生 3.6 万指纹 | 峰值太密 | 峰值上限 30/s |
| 票数只有 50（约 1%） | 密集段 Δt 只有 1–5 帧，±1 帧抖动就对不上 | Δt 下限 4 帧 + 量化 2 帧 |
| 置信度显示 0% | 用票数/查询数，分母过大 | 改为 票数/√查询数 再归一到 0–1 |
| 库外音频也报歌名 | 没有拒绝阈值 | 票数 < 20 判未识别 |

## 5. 局限与后续

| 局限 | 说明 | 后续方案 |
| --- | --- | --- |
| 清唱/翻唱识别不了 | 音色、调性都变了，指纹失效 | 加 chroma + DTW 旋律通道（QbH） |
| 变速 > 5% 失效 | 哈希依赖绝对时间差 | 需要变速不变特征 |
| 库只在当前浏览器 | IndexedDB 按站点隔离 | 可导出/导入 JSON |
| 建库耗时约 18 秒/首 | 全曲 STFT | 可只对副歌建库，或用 Worker |

## 7. 匹配详情展示（面向研究者）

识别完成后，面板会展开一块「匹配详情」，把匹配过程量化：

| 指标 | 含义 |
| --- | --- |
| 查询时长 / 提取峰值 / 峰值密度 | 指纹提取的规模，密度受"30 个/秒"上限约束 |
| 查询哈希 / 命中哈希 / 命中率 | 查询侧的哈希有多少在库中找到了同值；真匹配通常 >40% |
| 最高票数 / 次佳票数 / 领先倍数 | 投票分布的最高点与第二高点的差距 |
| 时间偏移 | 命中位置对应原曲的时间（mm:ss） |
| 投票分布图 | 横轴＝时间偏移，纵轴＝票数；真匹配有明显尖峰，误匹配是一条平坦噪声带 |
| 候选排名 | Top-5 (歌曲, 偏移)，可看出其余候选的票数量级 |
| 指纹参数 | 采样率、窗长、hop、门限、量化、阈值等完整参数表 |

**为什么这些指标有用**：

- 只看"识别成功"无法判断可信度；**领先倍数**和**分布尖峰**才是判据
- 命中率低但票数集中 → 说明片段被严重降质（如强噪声），仍可识别
- 命中率高但票数分散 → 通常是无调性素材（纯噪声/纯音乐），应拒绝
- 反例（库外音频）实测：命中率 7.1%、领先 1.3×、分布平坦 → 正确判为未识别

实测对比：

| 案例 | 命中率 | 最高票 | 次佳 | 领先 | 判定 |
| --- | --- | --- | --- | --- | --- |
| 加噪版 | 51.5% | 150 | 80 | 1.9× | ✅ |
| 反例 | 7.1% | 8 | 6 | 1.3× | ❌ |

## 8. 服务端化改造（前端不建库）

### 改了什么

| 之前 | 现在 |
| --- | --- |
| 前端选音频建库，指纹存 IndexedDB | 指纹存后端 SQLite（启动时从种子导入） |
| 前端面板有「选择音频并建库 / 清空指纹库」 | 面板只有「选择音频识别 / 录音识别」 |
| 匹配在浏览器内完成 | 前端只算查询哈希，匹配与投票在后端 |

### 分工与理由

浏览器有 WebAudio，能直接解码 MP3/WAV/M4A；Node 没有 ffmpeg 时无法解码音频。
所以：**解码与取指纹放前端，存储与匹配放后端**，部署零额外依赖。

### 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/fingerprint/library` | 返回歌曲数、指纹数、歌曲清单 |
| POST | `/api/fingerprint/match` | 入参 `{ hashes: [h, t, h, t, ...] }`，返回 best / candidates / distribution |

### 数据表

```sql
fingerprint_songs (id, title, duration_sec, hash_count, created_at)
fingerprint_hashes (song_id, h, t)  -- 主键 (song_id, h, t)，按 h 建索引
```

种子导入时主键去重，28,745 条原始指纹实际入库 24,899 条。

### 实测

| 案例 | 票数 | 命中率 | 耗时 |
| --- | --- | --- | --- |
| 原曲片段 | 123 | ~61% | 3s |
| 加噪版 | 125 | ~61% | 1s |
| 切断版 | 93 | 61.2% | 1s |

## 9. 旋律通道（清唱 / 哼唱识别）

### 为什么需要它

指纹匹配依赖"同一录音"的频谱峰值；清唱换了嗓音、可能换调，指纹票数只有个位数，必须换方法。

### 算法

```
建库：整曲 → 11.025kHz → STFT(2048/512) → 12 音级能量
     → 每 4 帧合并（5.38 帧/秒）→ 逐帧归一化 → 存 SQLite

识别：片段 → 同样的 chroma → 去全局均值 → 逐帧归一化
     → 在原曲序列上滑动 → 每个位置试 13 个移调（-6..+6）
     → 余弦相似度均值 → 最高者 → 相似度 ≥ 0.12 且 z ≥ 4.0 判命中
```

### 关键设计

| 设计 | 作用 |
| --- | --- |
| 去全局均值 | 纯音/噪声的 chroma 恒定，去均值后接近零向量，天然低分 |
| 移调搜索 ±6 | 清唱升/降调仍能对齐；chroma 对八度不敏感，男女声差八度无需处理 |
| 滑动窗口 | 唱任意片段都能定位，无需知道唱的是哪一段 |
| z 分数 | 衡量峰值相对整体分布的显著性 |

### 校准数据

| 样本 | 相似度 | z | 移调 | 判定 |
| --- | --- | --- | --- | --- |
| 原曲片段（0:50） | 0.951 | 15.73 | 0 | ✅ |
| 加噪版（SNR 12dB） | 0.950 | 15.70 | 0 | ✅ |
| 男声清唱（35s） | 0.159 | 4.44 | +5 | ✅ 旋律匹配 |
| 不相关音频（30s 噪声） | 0.099 | 3.81 | — | ❌ 正确拒绝 |

### 双通道协作

```
POST /api/fingerprint/match { hashes, chroma }
  → 指纹命中 → channel: "fingerprint"
  → 否则旋律命中 → channel: "melody"
  → 都不中 → accepted: false，同时返回两条通道得分
```

### 局限

| 局限 | 说明 |
| --- | --- |
| 相似度绝对值低 | 清唱 0.16，远低于原曲 0.95，判据依赖 z 分数 |
| 跑调敏感 | 偏差超过半音明显掉分 |
| 噪声环境 | 信噪比 < 5dB 时 chroma 被污染，需先降噪 |
| 时长 | 建议 10~35 秒 |

## 10. 误判修复：整首歌查询被认成目标曲

### 现象

把另一首歌（《第三人称》，同歌手不同曲，4 分 42 秒）整首提交，被判成《起风了》。

### 原因

指纹通道原来只用**绝对票数**判定（≥ 20 票）。整首歌查询会生成 27,035 个哈希，
随机碰撞在每个偏移上都能累积到几十票，于是 64 票越过了阈值。

### 数据

| 样本 | 票数 | 查询哈希 | 命中率 | 结论 |
| --- | --- | --- | --- | --- |
| 原曲片段 | 123 | 2,974 | 4.1% | 真匹配 |
| 加噪版 | 125 | 2,973 | 4.2% | 真匹配 |
| 切断版 | 93 | 1,774 | 5.2% | 真匹配 |
| 男声清唱 | 19 | 5,146 | 0.37% | 指纹失败 → 旋律通道 |
| **第三人称** | **64** | **27,035** | **0.24%** | **误判** |
| 噪声 | 8 | 8,254 | 0.1% | 正确拒绝 |

真匹配的命中率在 4% 以上，误判只有 0.24%，差一个数量级。

### 修复

指纹判定改为**双条件**：

```
接受 = 票数 ≥ 20  且  票数 / 查询哈希数 ≥ 1.5%
```

同时旋律通道本来就能拒绝它（相似度 0.0576 < 0.12，z 3.95 < 4）。

### 修复后结果

| 样本 | 指纹 | 旋律 | 最终 |
| --- | --- | --- | --- |
| 原曲片段 | 123 票（4.1%） | — | ✅ 指纹 |
| 加噪版 | 125 票（4.2%） | — | ✅ 指纹 |
| 切断版 | 93 票（5.2%） | — | ✅ 指纹 |
| 男声清唱 | 19 票（0.37%） | 0.159 / z 4.44 | ✅ 旋律 |
| 第三人称 | 64 票（0.24%）❌ | 0.058 / z 3.95 ❌ | ❌ 正确拒绝 |
| 噪声 | 8 票（0.1%）❌ | 0.099 / z 3.81 ❌ | ❌ 正确拒绝 |

### 经验

**绝对票数不是尺度无关的判据**：查询越长，哈希越多，碰撞票数越高。
必须用「命中率」或「相对显著性」这类归一化指标。
